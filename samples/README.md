# AuthorizationInterceptor Sample

This sample shows how `AuthorizationInterceptor` manages authorization headers for outbound `HttpClient` calls.

The solution contains two APIs:

- `TargetApi`: a mock protected API. It issues short-lived OAuth-like tokens through `/auth`, refreshes them through `/refresh`, and protects `/data`.
- `SourceApi`: the client application. It configures multiple named `HttpClient` instances, each one demonstrating a different AuthorizationInterceptor setup, then exposes test endpoints that call `TargetApi/data`.

The main idea is to call the same protected `TargetApi` endpoint through different `HttpClient` configurations and compare how headers are generated, cached, refreshed, and isolated.

## Running the Sample

Start `TargetApi` first:

```bash
dotnet run --project TargetApi
```

Then start `SourceApi`:

```bash
dotnet run --project SourceApi
```

Default local URLs:

- `TargetApi`: `http://localhost:5121`
- `SourceApi`: `http://localhost:5117`
- `SourceApi` Swagger UI: `http://localhost:5117/swagger`
- `TargetApi` Swagger UI: `http://localhost:5121/swagger`

`SourceApi` also configures Redis-backed distributed cache with `localhost:6379`. Endpoints that use distributed or hybrid cache require Redis to be running.

## TargetApi Endpoints

| Endpoint | Description |
| --- | --- |
| `POST /auth` | Creates a new mock user authorization and returns access token, refresh token, token type, and expiration data. The optional `x-mycustom-header` request header is used as the user name. |
| `POST /refresh?refresh={refreshToken}` | Receives a refresh token and returns a renewed authorization when the refresh token is known. Returns `401` when the token is missing or invalid. |
| `GET /data` | Protected endpoint. Requires a valid `Authorization: Bearer {accessToken}` header. Returns `401` when the header is missing, unknown, or expired. |

## SourceApi Endpoints

All `SourceApi` endpoints below call `GET /data` on `TargetApi`. The difference is the named `HttpClient` configuration used for each call.

| Endpoint | HttpClient | What it demonstrates |
| --- | --- | --- |
| `GET /test/TargetApiWithNoInterceptor` | `TargetApiWithNoInterceptor` | Uses AuthorizationInterceptor without a cache interceptor. Headers are generated by the authentication handler and refreshed when `TargetApi` returns `401`, but they are not stored in memory, distributed, or hybrid cache. |
| `GET /test/TargetApiWithMemoryCache` | `TargetApiWithMemoryCache` | Uses `UseMemoryCacheInterceptor()`. Authorization headers are cached in the local process until their real expiration. This is the simplest cache option for single-instance applications. |
| `GET /test/TargetApiWithDistributedCache` | `TargetApiWithDistributedCache` | Uses `UseDistributedCacheInterceptor()`. Authorization headers are stored through `IDistributedCache`, allowing multiple application instances to share the same authorization data. |
| `GET /test/TargetApiWithHybridCache` | `TargetApiWithHybridCache` | Uses `UseHybridCacheInterceptor()`. Authorization headers are stored through hybrid cache, combining local and distributed cache behavior. |
| `GET /test/TargetApiWithCustomInterceptors` | `TargetApiWithCustomInterceptors` | Uses memory cache, distributed cache, and three custom interceptors. This demonstrates how custom `IAuthorizationInterceptor` implementations can participate in the lookup and update chain. |
| `GET /test/TargetApiWithData1` | `TargetApiWithData1` | Creates the authentication handler with custom constructor data: `SomeData("data1")`. This demonstrates passing different dependencies or values into the auth handler while using the same target API. |
| `GET /test/TargetApiWithData2` | `TargetApiWithData2` | Same idea as `TargetApiWithData1`, but passes `SomeData("data2")`. This shows how two named clients can authenticate with different context data. |
| `GET /test/TargetApiWithCacheKeyBuilder` | `TargetApiWithCacheKeyBuilder` | Uses memory cache plus `CacheKeyBuilder`. The cache key suffix is built from the incoming `x-mycustom-header` request header, so the same `HttpClient` can keep separate cached authorization headers per request-specific value. |

## CacheKeyBuilder Scenario

`TargetApiWithCacheKeyBuilder` is useful when the same target API and same named `HttpClient` are reused for different users, tenants, stores, or organizations.

In this sample, the cache key suffix comes from `x-mycustom-header`:

```csharp
builder.Services.AddHttpClient("TargetApiWithCacheKeyBuilder")
    .AddAuthorizationInterceptorHandler<TargetApiAuthClass>(opt =>
    {
        opt.UseMemoryCacheInterceptor();
        opt.CacheKeyBuilder = context =>
            $"{context.HttpContext!.Request.Headers["x-mycustom-header"]}";
    })
    .ConfigureHttpClient(c => c.BaseAddress = new Uri("http://localhost:5121"))
    .AddHeaderPropagation(configure => configure.Headers.Add("x-mycustom-header"));
```

Calling `GET /test/TargetApiWithCacheKeyBuilder` with different `x-mycustom-header` values creates separate cached authorization headers, even though the endpoint uses the same named `HttpClient`.
